# Reflections

## Reflection 1 — Building one shared way of working

At the start of the project, we were concerned that the Organizer, Venue Administrator, and Attendee features would be developed as three separate pieces of work. If each person prompted the agent differently, we could easily end up with inconsistent assumptions, testing standards, and UI designs. We therefore placed the shared agent configuration in the repository so that everyone worked with the same starting point.

We used `AGENTS.md` for the rules that should apply to every task. It tells the agent to treat the user task, MP2 specification, agreed team decisions, and current code as the authoritative sources. It also tells the agent not to fill in unresolved business rules, such as the cancellation cutoff or check-in window, without asking us first. Other rules prevent secrets from appearing in logs and stop the agent from committing, pushing, or overwriting a teammate’s files unless we explicitly request it.

We kept task-specific procedures separate under `.agents/skills/`. This separation became useful as the project grew because the agent did not need the same instructions for every task. We used `requirements-and-acceptance` when a rule was still unclear, `test-driven-implementation` once the expected behaviour had been agreed, and `code-review-and-verification` when we needed to investigate a diff or an ownership problem before changing code. For JavaFX screens, `desktop-ui-polish` gave the agent a shared set of layout and styling expectations. We later added security, database, and observability skills when we noticed that those concerns were appearing across multiple roles rather than in only one feature.

We also realised that instructions alone were not enough for the rules we considered important. The agent could misunderstand or overlook a written instruction, so we added hooks that deny subagents, block destructive shell commands, and prevent access to secret files. This gave us a clearer distinction: `AGENTS.md` defines the boundaries, a skill guides the task, and a hook enforces selected boundaries while the agent is running.

The benefit of this setup became clearer during implementation. Requirements reviews stopped us from building directly on guesses. Cancellation behaviour remained conditional until we had agreed on the cutoff and ownership rules. Venue requests were kept within the existing submitted-and-approved workflow, and the check-in timing stayed unresolved until the group made a decision. Once a rule was settled, the test-driven skill became more useful because the agent could work from a concrete expected result. Features such as creating and editing events, capacity updates, volunteers, clubs, announcements, publishing, draft deletion, registration, and venue approval began with a failing test followed by a focused implementation.

The cross-role database tests were especially useful. The individual role tests passed when run separately, but the combined suite exposed an interaction that none of us had noticed: submitting a second venue request for an already approved event caused the administrator’s approval flow to fail. This reminded us that a consistent workflow does not prevent all bugs. Its value is that assumptions and interactions become visible earlier and in a form that the whole group can review.

Overall, the main improvement was not simply that the agent produced code more quickly. It was that the group had one repeatable process for deciding when the agent should clarify a requirement, write a test, review a change, or stop. That made the work across the three roles easier to compare and reduced the number of decisions the agent invented on its own.

## Reflection 2 — Turning a vague UI skill into something testable

Our first version of the UI skill sounded reasonable to us. It told the agent to tidy a JavaFX layout, align the form, and match the rest of the application. However, the first Organizer screen produced with those instructions showed that the skill was too vague. The form remained compressed, some labels were cut off, the outer Home header and inner sidebar appeared at the same time, and the New event action did not consistently open a blank form.

The problem was that “make the screen cleaner” described the result we wanted without explaining what the agent had to inspect. The agent could make a few cosmetic changes and still consider the task complete. As a group, we needed a way to tell the difference between a response that sounded convincing and one that had actually followed the review process.

We therefore created `tools/graders/grade_desktop_ui_skill.py`, a deterministic Python grader using only the standard library. It does not call another model. Instead, it reads the JSONL trace from an agent run and returns `PASS` or `FAIL`. For the U1 review task, it checks that the trace exists, that `desktop-ui-polish` was used, that no file under `src/` was edited, and that the final response identifies an actual layout problem. It also checks for the shared shell colours, a before-and-after checklist, and a clear statement that club creation is outside the task’s scope.

We tested the grader itself using `unittest` and small synthetic traces. A complete trace passes when the agent reads the skill and identifies the double navigation chrome, restricted form width, truncated `GridPane` labels, and the shared colours `#172033` and `#f7f9fc`. It must also include the checklist and avoid proposing club CRUD. In contrast, a response that mentions the colours but does not identify a layout fault fails `LAYOUT_FINDINGS`. A response that proposes a complete club-management interface fails `SCOPE_RESPECTED`. A trace that edits `OrganizerEventView.java` during the review-only task fails `NO_IMPLEMENTATION`, even if its final explanation appears correct.

These failures showed us exactly what the original skill was missing. We revised it to require one navigation shell, columns that grow with the window, fully visible labels, consistency with the Venue Administrator colours, obvious primary actions, and an explicit list of features that must not be invented. This was more useful than simply adding more general instructions because each addition came from a failure we had already observed.

When we ran the revised skill again, we first requested a review without implementation. This time, the agent identified the double header, missing column constraints, and unclear New event behaviour. We then allowed it to implement the reviewed changes. The follow-up moved Home into the sidebar, widened the form, and made New event enter create mode while highlighting the correct navigation item.

This gave us a concrete improvement we could trace back to the skill revision. The first version had asked for a polished screen but left important defects unnoticed. The revised version required the agent to name those defects before editing anything. We later reused the same skill on Organizer, Venue Administrator, and Attendee screens, which helped the group maintain a more consistent shell across the application. At the same time, this experience taught us that a grader can make a skill more precise, but it can only evaluate the evidence it has been designed to inspect.

## Reflection 3 — Learning when the agent should stop and ask us

One of the most important lessons for us was that the agent was most useful after the group had made the necessary product decisions. When a business rule was still open, allowing the agent to continue usually created more work rather than saving time.

This happened with cancellation and check-in. The agent was ready to supply a cutoff or a valid time window even though the team had not agreed on either rule. Instead of accepting a plausible value, we stopped the implementation and used `requirements-and-acceptance` to record the missing decision and keep the acceptance criteria conditional. Only after the group settled the rule did we move to `test-driven-implementation`.

Venue requests revealed a similar issue. An early assumption was that an event could not submit another venue request after one had already been approved. However, the current code allowed the second request, and the cross-role tests showed that it broke the administrator’s later approval flow. The agent could identify the inconsistency, but it could not decide which behaviour the product should support. We had to examine the workflow as a group, choose the intended rule, and then give the agent a definite outcome to implement.

We also had to redirect the agent when its proposed solution did not match how we wanted users to interact with the application. For capacity management, the agent initially introduced a separate Capacity screen. Although this could have worked technically, it added a new navigation path that we did not want. We clarified that capacity should be updated within the existing edit flow, with no additional button or page, and the agent then reworked the feature around that decision.

Publishing exposed a different boundary. The first implementation was made on a branch that we later discarded, so the change had to be reapplied on the correct branch without allowing the agent to perform Git operations. This reinforced why we had included ownership and version-control restrictions in `AGENTS.md`. The agent could help reconstruct the change, but the group remained responsible for deciding where the work belonged and how it should be integrated.

Our skill structure also changed as we learned from these situations. One of our first ideas was an Attendee-specific skill, but it became clear that requirements review, test-driven implementation, and code review were not unique to one role. We replaced that narrow approach with shared workflow skills that could be used across Organizer, Venue Administrator, and Attendee tasks. The UI skill followed the same pattern: “tidy the layout” was too broad to guide a reliable review, so we replaced it with concrete checks derived from actual failures.

From these experiences, we learned that a skill can keep the agent on a process, but it cannot make a product decision for the team. Autonomy helped once the expected behaviour was settled because the agent could move from a failing test to a focused fix. Before that point, the safer and usually faster choice was to make the agent stop, state what was unresolved, and return the decision to us.

## Reflection 4 — What our grader still cannot tell us

Although the desktop UI grader improved the skill, we also learned that passing the grader does not mean the screen itself is correct. `grade_desktop_ui_skill.py` evaluates the JSONL trace from the U1 review task. It can confirm that the correct skill was used, that the agent identified the expected layout issues, that club creation remained outside the scope, and that no source file was edited during a review-only run. It also checks that the response includes the shared shell colours and a before-and-after checklist.

These checks tell us whether the agent followed the review procedure. They do not tell us whether the JavaFX application actually works. The grader never opens the window, resizes it, clicks New, Save, or Home, or checks whether the colours are visible on the rendered screen. An agent could also mention the expected terms in its response without fully understanding the layout. In other words, the grader can verify trace compliance, but it cannot independently verify the final user experience.

We saw this distinction during the Organizer work. The revised skill correctly identified the double header and compressed form, but we still had to run the application and inspect the result ourselves. We needed to confirm that the labels remained readable, that the navigation state changed correctly, and that the screen still worked at different window sizes. A passing review trace was useful evidence, but it was not enough to approve the implemented screen.

If we repeated this project, we would keep the existing grader for the review-only stage and add a separate verification stage after implementation. The trace grader’s `OVERALL: PASS` would mean only that the agent followed the review skill. Completion of the UI task would additionally require `./gradlew classes`, the relevant automated tests, and a manual run using `./gradlew run`. We would record whether the group resized the window, checked all labels, tested the primary buttons, and compared the screen with the Venue Administrator shell. Screenshots at two window sizes could also be stored alongside the interaction log as evidence.

We would also run the same evaluation more than once and on more than one screen. A single successful U1 trace shows that the revised skill worked in that case, but it does not prove that it will trigger correctly or produce the same quality every time. Repeating the task across the three roles, including a few unseen screens, would give us stronger evidence that the skill generalises beyond the example used to improve it.

The main lesson for us was that process evidence and outcome evidence answer different questions. The grader tells us whether the agent followed the workflow we designed. Compilation, automated tests, screenshots, interaction checks, and human review tell us whether the resulting software is actually acceptable. A reliable single-agent workflow needs both, and the group still remains responsible for the final judgement.
