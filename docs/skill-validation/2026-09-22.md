## T1 — test-driven implementation

Synthetic evaluation task: in a scratch in-memory registration book, first
registration returns true, duplicate registration returns false, and duplicate
attempts leave the registration count unchanged. All policy needed by this narrow
fixture is supplied; no capacity, persistence, or concurrency claim is made.

The starting fixture used a `HashSet<String>` and this method:

```java
boolean register(String attendee) {
    attendees.add(attendee);
    return true;
}
```

A standalone Java test runner checked three observable cases on fresh instances:

1. First registration of `alice` returns true and size is one.
2. A second registration of `alice` returns false.
3. Registering `alice` twice leaves size equal to one.

Command, run before and after the change in an isolated temporary directory:

```sh
javac -d classes RegistrationBook.java RegistrationBookTest.java && java -cp classes RegistrationBookTest
```

Observed red result: compilation succeeded; two cases passed and one failed with
`duplicate should return false`; process exit 1. This was a behavioral assertion
failure, not a toolchain or compilation error.

The minimal fix was:

```java
boolean register(String attendee) {
    return attendees.add(attendee);
}
```

Observed green result: three cases passed, zero failed; process exit 0. No further
refactoring was needed. The assertion checked the public outcome and count, rather
than merely whether `HashSet.add` was called.

The scratch exercise used the available Java 21.0.10 compiler/runtime and an
explicit assertion runner with no dependencies. It was not the Java 25 Gradle/JUnit
MP2 test suite. This exception applies only to the isolated evaluation fixture;
real implementation must use the project's test framework and required JDK.

## C1 — code review and verification

Synthetic contract: only a registration's owner may cancel it, and a denied
cancellation leaves the registration intact. Review fixture:

```java
// owners maps registration IDs to owner IDs.
boolean cancel(String actor, String registrationId) {
    return owners.remove(registrationId) != null;
}
```

Finding: the fixture's `CancellationService.cancel` ignores `actor`. With
`registration-1` owned by `alice`, calling `cancel("bob", "registration-1")`
returns true and removes Alice's registration. A focused correction would enforce
the supplied ownership contract before mutation; real storage would also need to
preserve that check atomically with the mutation.

Reproduction command in the isolated directory:

```sh
javac -d classes CancellationService.java CancellationReviewRepro.java && java -cp classes CancellationReviewRepro
```

Observed output:

```text
Expected: cancelled=false, exists=true
Actual: cancelled=true, exists=false
AssertionError: Non-owner cancelled another attendee's registration
```

The process exited 1 as expected for the seeded defect. The review exercise did
not fix the fixture. This is a demonstrated defect in deliberately faulty sample
code, not a claim that the MP2 application contains that implementation.
